# Datos históricos: aceptación pendiente

Preparado al cerrar el bloque de interacción. **La implementación de este bloque
no empezó**; registrar hora real al comenzar y publicar la lista actualizada.

El plan principal exige conservar datos reales, procedencia y recuperación.
Exportar105 registros de un ensayo Chroma o migrar una base sintética no equivale
a aceptar la migración del historial del usuario.

1. Leer inventario/recibos ya disponibles y localizar los datos históricos reales
   con inspección de sólo lectura. Separar evidencia, suposición y ausencia;
   no imprimir credenciales ni volver a investigar contratos ya comprobados.
2. Identificar versión y disposición SQLite/Chroma/adjuntos antes de elegir
   lector. Trabajar sobre copia consistente identificada; no convertir ni abrir
   para escritura las fuentes originales durante el ensayo.
3. Comprobar conteos, contenido, relaciones, procedencia, archivos y límites del
   lector aislado. Reusar las migraciones y el aislamiento actuales; corregir
   brechas funcionales, documentando módulos/clases/métodos para Ken.
4. Probar el recorrido instalado y la recuperación de la copia sin reactivar
   autoridad antigua ni convertir registros históricos en trabajo nuevo.
   Conservar informes de ausencias/incompatibilidades en vez de fabricar datos.
5. Registrar qué historial real se cubrió y qué falta. Si no se puede localizar
   la fuente necesaria, pedir sólo esa información y avanzar en evaluaciones o
   páginas independientes. No declarar migración completa con datos inventados.

Después: evaluaciones —incluida comunicación U08, que recibió una evaluación
humana negativa—, aceptación de12 páginas, dependencias/distribución. Al final:
detalles aplazados, C10/DD116, DD120, suite global y revisión independiente.
